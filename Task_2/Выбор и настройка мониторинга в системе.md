### Мотивация
В данный момент мы явно налблюдаем проблемы в системе, которые влияют как на внешних и внутренних пользвоватлей, так и на пользователей API, что приводит к репутационным рискам и финансовым потерям в результате потери части заказов. Для выявления проблемных мест и своевременного реагирования на возникающие аномалии мы введем систему мониторинга. Начнем с необходимого минимума, но с возможностью дальнейшего расширения в случае возникновения потребности.

### Выбор подхода к мониторингу

Для сервернов: 

- Потребление ресурсов процессора, памяти и диска - т.к наблюдаем деградацию latency и есть подозрение на потерю данных в результате перегрузки сервисов, нам необходимо следить за нагрузкой
- В дальнейшем можно использовать подход USE в полном объеме

Метрики:
- CPU % for shop API
- CPU % for CRM API
- CPU % for MES API
- Memory Utilisation for shop API
- Memory Utilisation for CRM API
- Memory Utilisation for MES API
- Memory Utilisation for shop db instance
- Memory Utilisation for MES db instance
- Memory Utilisation for RabbitMQ
- Size of S3 storage
- Size of shop db instance
- Size of MES db instance

Для сервисов мы будем использовать подход RED:

- Requests Rate - даст нам представление о пропускной способности сервиса. Мы будем отслеживать пиковый трафик и сможем прогнозировать, сколько нужно ресурсов (метки: method, status)
- Errors - будем отслеживать частоту ошибок, неправильные, неполные или неожиданные запросы пользователей
- Duration - будем получать данные о количество времени, которое уходит на выполнение одного запроса. Распределенная трасировка поможет нам отслеживать запрос пользователя в разных сервисах и измерять время, которое заняли события в каждом сервисе.

Метрики:
- Number of dead-letter-exchange letters in RabbitMQ
- Number of message in flight in RabbitMQ
- Number of requests (RPS) for internet shop API (method, status, code, url)
- Number of requests (RPS) for CRM API (method, status, code, url)
- Number of requests (RPS) for MES API (method, status, code, url)
- Number of requests (RPS) per user for internet shop API
- Number of requests (RPS) per user for CRM API
- Number of requests (RPS) per user for MES API
- Number of connections for shop db instance
- Number of connections for MES db instance
- Response time (latency) for shop API
- Response time (latency) for CRM API
- Response time (latency) for MES API
- Number of simultanious sessions for shop API
- Number of simultanious sessions for CRM API
- Number of simultanious sessions for MES API

Этих метрик нам будет достаточно для того что бы выявить проблемные места в текущей архитектуре и своевременно реагировать на возникающие аномалии в системе.

### План действий

1. Создать единую точку входа API Gateway
2. Развернуть Prometheus
3. Настроить сбро метрик с нужных сервисов
4. Развернуть Jaeger для распределенной трасировки

### Методы реагирования на превышения порога насыщенности

- для метрик серверных ресурсов установим порог в 75% при привышении которого будем отправлять сообщения дежурным командам в соответствующие каналы
- RabbitMQ `messages.ready`, `messages.unacked`, если > 10 000 сообщений в одной очереди дольше 10 минут или `dead-letter-queue` > 100 сообщений/мин - Автоматический алерт в чат
- Storage > 85% заполнения S3 или диска базы данных - Автоматический алерт в чат
- DB Connections > 80% от максимального пула соединений - Автоматический алерт в чат

В дальнейшем нужно будет настроить автоматическое масштабирование, пока все делаем вручную.

### Анализ

Сейчас существует проблема, что заказы часто находятся в непонятном состоянии или зависают на каком-то сервисе внутри IT-ландшафта. 
Для того что бы найти проблемные места, нам нужно настроить трейсинг запросов связанных с изменением статуса заказов. 

В этом процессе участвуют следующие сервасы:
    - онлайн-магазин
    - MES
    - CRM
    - Message Queue

#### Какие данные должны попадать в трейсинг

Общие технические данные:

    - Trace ID — единый идентификатор сквозного запроса (передаётся через все сервисы).
    - Span ID — идентификатор конкретной операции внутри сервиса.
    - Parent Span ID — связь с родительским вызовом.
    - Сервис-источник (service name) — откуда пришёл вызов (shop, CRM, MES, MQ).
    - Operation name — название выполняемой операции (например, ChangeOrderStatus, PublishMessage, UpdateDBRecord).
    - Timestamps (start, end) — начало и конец операции.
    - Duration — длительность выполнения.
    - Status / Error flag — успех или ошибка (с кодом и текстом).

Данные по бизнес-контексту (ключевые теги):

    - Order ID — идентификатор заказа (основная бизнес-связка).
    - User ID (или customer ID) — если инициатор известен.
    - New Status и Previous Status — какое переключение происходило.
    - Channel — источник запроса (например, api, crm_ui, batch_job).

### Мотивация

В текущей архитектуре бизнес-процессов изменение статуса заказа проходит через несколько сервисов: интернет-магазин, CRM, MES и очередь сообщений. Ошибки или задержки на любом из этапов приводят к тому, что заказ может застрять в неопределённом состоянии. Это напрямую влияет на доверие клиентов и может вызвать финансовые потери из-за несвоевременной обработки заказов.

Внедрение распределённого трейсинга позволит:

    - Сократить время расследования инцидентов — станет понятно, в каком сервисе именно возникла задержка или ошибка.
    - Повысить прозрачность бизнес-процессов — каждая операция по заказу будет прослеживаться сквозь все системы.
    - Снизить финансовые риски — за счёт более быстрой реакции на проблемы.
    - Упростить оптимизацию — можно измерить реальное время обработки заказов и выявить узкие места

#### Метрики, на которые повлияет внедрение трейсинга

Технические:

    - Среднее время отклика (latency) по всей цепочке изменения статуса заказа — от запроса пользователя до обновления в MES.
    - Время обработки на каждом этапе (Shop API, CRM, MQ, MES) — поможет находить медленные сервисы.
    - Частота ошибок по конкретным сервисам и операциям — где чаще всего падает логика.

Бизнесовые:

    - Доля заказов, обработанных без задержек — ключевой KPI для клиентского опыта.
    - MTTR (Mean Time To Resolution) — среднее время на устранение инцидента: с трейсингом оно сокращается.


### Предлагаемое решение

В реализации трейсинга мы будем использовать Jaeger. Для этого нам нужно будет развернуть отдельный инстанс Jaeger со своим хранилищем данных. Дополнительно нужно будет донастроить приложения и сервисы для отправки данных в инстанс Jaeger. Для визуализации собранных данных будем использовать Jaeger-UI

### Компромиссы

#### Проприетарные или закрытые системы

Если в цепочке участвуют сторонние системы (например, SaaS-платформы, облачные API или проприетарные продукты), в которых нет встроенной поддержки OpenTelemetry/Jaeger, то:

добавление трейсинга может быть невозможно или потребует дорогостоящей кастомизации (SDK, прокси, адаптеры).

#### Высокая стоимость внедрения

Трассировка подразумевает интеграцию в каждый сервис и его зависимости. В системах с устаревшей кодовой базой (legacy) доработка может быть слишком дорогой и рискованной — проще ограничиться логированием и метриками.

#### Отсутствие культуры эксплуатации

Если команда не готова регулярно пользоваться трейсингом (нет практики работы с Jaeger, нет процессов реагирования), то вложения в инструмент не окупятся. В таких случаях целесообразно сначала построить базовый мониторинг (метрики, алерты, логи), а потом переходить к трейсингу.

### Безопасность

#### Аутентификация и авторизация

Корпоративная аутентификация — доступ в систему трейсинга (Jaeger UI) смогут получить только сотрудники компании с корпоративной учётной записью.

Ролевая модель доступа (RBAC):

Роль Поддержка — просмотр трейсинга для расследования инцидентов.
Роль Разработчик — доступ к трассировкам только в пределах своих сервисов.
Роль Администратор — настройка и управление системой трейсинга.

#### Ограничение внешнего доступа

- Доступ к UI и API Jaeger разрешён только из внутренней сети (VPN или корпоративный прокси).
- Внешний доступ возможен только через защищённый канал (TLS + VPN) и с многофакторной аутентификацией.

#### Шифрование и защита данных

- Передача данных между агентами трейсинга и коллектором — только по TLS.
- Хранение данных в базе трейсинга (например, Elasticsearch, ClickHouse) с шифрованием «на диске» (at rest).
- Исключение попадания PII (персональных данных пользователей) в теги и логи трейсинга — допустимо хранить только технические идентификаторы (Order ID, Request ID).

#### Контроль и аудит

- Ведение логов всех действий пользователей внутри системы трейсинга (кто вошёл, что просматривал).
- Регулярная проверка актуальности ролей и учётных записей (удаление неактивных сотрудников).

#### Минимизация избыточного доступа

- Использование политики least privilege — каждый сотрудник получает только тот уровень доступа, который необходим для работы.
- Для внешних подрядчиков или интеграционных команд доступ предоставляется временно, через отдельные учётные записи с ограниченными правами.

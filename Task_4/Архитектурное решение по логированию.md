### Анализ

1. Shop API

    INFO

- order_id, customer_id, old_status, new_status, timestamp — при изменении статуса заказа.
- user_id, endpoint, http_method, response_code, latency — при выполнении запросов API.
- session_id, auth_status — при авторизации пользователя.

2. CRM

    INFO

- order_id, crm_task_id, old_status, new_status, timestamp — при изменении данных о заказе.
- user_id, operation_type, result — при действиях сотрудников.
- db_query_duration, rows_updated — для ключевых транзакций (например, массовые изменения заказов).

3. MES

    INFO

- order_id, mes_job_id, old_state, new_state, timestamp — при обновлении производственных задач.
- worker_id, operation_type, duration — при выполнении производственных операций.
- message_id, processing_status — при обработке событий из очереди.

4. Message Queue (RabbitMQ)

    INFO

- message_id, queue_name, producer_service, timestamp — при публикации сообщений.
- message_id, consumer_service, timestamp, ack/nack/retry — при обработке сообщений.
- queue_length, lag — при превышении порога длины очереди.

5. Логирование ошибки, приводящие к отклонению операции

- не удалось сменить статус заказа
- база данных вернула ошибку
- сообщение не доставлено в очередь


### Мотивация

- возможность расследовать спорные ситуации (например, клиент утверждает, что статус заказа был изменён некорректно);
- доказательную базу при инцидентах и аудитах;
- снижение времени на поиск и устранение ошибок (корреляция логов с трейcингом и метриками);

### Предлагаемое решение

Предлогается использовать стек ELK. Для этого:
- в сервисах Shop API, CRM API, MES API, Message queue, добавим Filebeat
- развернем сервис Logstash
- развернем сервис Elasticsearch
- развернем сервис Kibana

### Безопасность

#### Аутентификация и авторизация

Корпоративная аутентификация — доступ в систему логирования (Kibana Dashboards) смогут получить только сотрудники компании с корпоративной учётной записью.

Ролевая модель доступа (RBAC):

Роль Поддержка — просмотр логов сервисов для расследования инцидентов.
Роль Разработчик — доступ к логам только в пределах своих сервисов.
Роль Администратор — настройка и управление всей системой логирования, индексами и политиками хранения.
Роль Безопасность — доступ ко всем логам для целей аудита и контроля безопасности.

#### Шифрование и защита данных

- Передача данных от агентов логирования (Fluent Bit/Vector) к коллектору и далее в Elasticsearch/OpenSearch осуществляется только по TLS.
- Хранение данных в кластере Elasticsearch/OpenSearch с шифрованием «на диске» (at rest) на уровне хранилища.
- Исключение попадания PII (персональных данных) в логи: в индексах допускается хранение только технических идентификаторов (Order ID, Request ID). Личные данные пользователей должны маскироваться или хешироваться.

#### Контроль и аудит

- Ведение логов всех действий пользователей внутри Kibana/OpenSearch: вход, просмотр, экспорт данных, изменение дашбордов.
- Регулярная проверка и пересмотр актуальности ролей и учётных записей (удаление неактивных сотрудников, блокировка уволенных).
- Настройка алертов на подозрительную активность: массовый экспорт данных, систематический поиск по полям с потенциально чувствительной информацией.

#### Минимизация избыточного доступа

- Использование политики least privilege — каждый сотрудник получает только тот уровень доступа, который необходим для работы.
- Для внешних подрядчиков или интеграционных команд доступ предоставляется временно, через отдельные учётные записи с ограниченными правами.

### Политика хранения логов

#### Структура индексов

Для обеспечения удобного поиска и управления логами индексы будут разделяться по системам и дате.
Пример схемы именования индексов:

- logs-shop-* — логи онлайн-магазина.
- logs-crm-* — логи CRM.
- logs-mes-* — логи MES.
- logs-mq-* — логи Message Queue.

Каждый индекс будет содержать подиндиксы по дате (например, logs-shop-2025.09.22), что позволит быстро удалять или архивировать данные по сроку хранения.


#### Сроки хранения

Политика хранения зависит от категории логов:

1. Бизнес-логи (изменение статуса заказов, события CRM, MES):
    - Hot storage (оперативное хранение): 7 дней (быстрый доступ для расследований).
    - Warm storage (снижение стоимости): до 90 дней.
    - Cold storage (только чтение, дешёвое хранилище): до 180 дней.

Удаление: после 180 дней.

2. Логи безопасности (аутентификация, доступы, нарушения):

   - Хранение не менее 365 дней в cold storage (регуляторные требования, расследования инцидентов).

3. Инфраструктурные логи (k8s, системные сервисы, MQ в технической части):

    - 30–60 дней в warm storage.
    - Удаление после 90 дней.

4. Размеры индексов и ротация

Каждый индекс будет роллироваться ежедневно или при достижении лимита в 50 GB, в зависимости от того, что наступит раньше.

Для высоконагруженных сервисов (Shop API, MQ) лимит может быть снижен до 10–20 GB на индекс для оптимизации поиска.

Используется ILM (Ind˜ex Lifecycle Management) с фазами: hot → warm → cold → delete.

### Система анализа логов

Для того что бы построить систему анализа логов мы можем добавить в систему:

- Elasticsearch Watcher для мониторинга аномалий и алертинга
- Интеграции со Slack, Email или Telegram

Что стоит мониторить:

- Ошибки приложения 
- Рост количества ошибок 
- Отсутствие логов от критичного сервиса
- Наличие запрещённых данных в логах 
- Резкий рост логов безопасности 

Примеры аномалий, которые стоит отслеживать:

- Бизнес-метрики:
    - Резкий скачок событий OrderCreated (например, с 4 → 10 000 за секунду).
    - Массовые изменения статуса заказов (возможно, ошибка интеграции MES).
    - Аномальное количество отказов платежей за короткий период.

- Инфраструктурные метрики:
    - Взрывной рост количества запросов от одного IP (признак DDoS или бота).
    - Увеличение размера логов более чем в X раз по сравнению со средним.
    - Систематические таймауты в CRM или MQ.

- Безопасность:
    - Множественные неуспешные логины.
    - Попытка доступа к несуществующим API (сканирование).
    - Наличие команд SQL-инъекций в запросах.
